# Стек backend приложения напоминаний

## Назначение

Backend хранит дела и расписание, а в назначенное время отправляет push-уведомления на устройства пользователя. Next.js PWA отвечает за интерфейс и регистрацию push-подписки. Сервер является источником истины: закрытие или перенос дела должно отменять либо пересчитывать будущие отправки.

## Выбранный стек

| Область | Технология | Роль |
| --- | --- | --- |
| HTTP API | Python, FastAPI, Pydantic | REST API для PWA, валидация и схема OpenAPI |
| Основная база | PostgreSQL | Пользователи, дела, правила повторов, устройства, запланированные отправки и журнал доставки |
| ORM и миграции | SQLAlchemy 2, Alembic | Работа с PostgreSQL и версионирование схемы |
| Очередь фоновых задач | Celery | Запуск фоновых обработчиков, повторы и маршрутизация задач по очередям |
| Брокер | RabbitMQ | Надёжная передача сообщений от API/планировщика к Celery workers |
| Планировщик Celery | Celery Beat | Периодический запуск диспетчера, который находит наступившие отправки в PostgreSQL |
| Push | Web Push с VAPID; Python-библиотека `pywebpush` | Шифрование и отправка push-подписок браузера в push-сервис платформы |
| Конфигурация | Переменные окружения, Pydantic Settings | Секреты и настройки окружений |
| Локальный запуск | Docker Compose | API, worker, Beat, PostgreSQL и RabbitMQ |

Версии библиотек следует зафиксировать в lock-файле при реализации и регулярно обновлять. VAPID private key, пароль базы, RabbitMQ credentials и секреты аутентификации хранятся только в секретах окружения, не в репозитории.

## Сервисы

В первой версии это один кодовый проект и один контейнерный образ с несколькими командами запуска:

- `api` — FastAPI и HTTP-маршруты;
- `worker` — Celery workers, выполняющие отправку push и другие фоновые операции;
- `beat` — один экземпляр Celery Beat, периодически запускающий диспетчер напоминаний;
- `postgres` — постоянное хранилище;
- `rabbitmq` — брокер задач.

Beat должен запускаться в одном экземпляре, чтобы избежать лишнего дублирования периодических запусков. Worker можно масштабировать отдельно от API.

## Как доставляется напоминание

1. API записывает дело и его параметры в PostgreSQL. Для одноразового дела сохраняется время отправки; для повторяющегося — правило и следующие рассчитанные срабатывания.
2. Celery Beat периодически ставит задачу диспетчера.
3. Диспетчер находит наступившие и ещё не обработанные отправки в PostgreSQL и передаёт их Celery worker-ам.
4. Worker повторно проверяет актуальное состояние дела, отправляет Web Push активным подпискам пользователя и сохраняет результат попытки.
5. Временные ошибки приводят к повтору с увеличивающейся задержкой. Недействительные подписки помечаются отозванными. После успеха или исчерпания попыток фиксируется итоговый статус.
6. При выполнении, удалении или переносе дела API обновляет записи расписания. Worker проверяет актуальность отправки перед отправкой, поэтому уже поставленная в RabbitMQ задача не должна уведомить о завершённом деле.

Для расписания не следует полагаться только на Celery-задачи с далёким временем `eta`. Долгосрочное расписание остаётся в PostgreSQL, а Celery получает работу по мере наступления времени. Это позволяет восстановить отправки после перезапуска и корректно обрабатывать изменение дела.

## Основные данные PostgreSQL

- `users` — учётная запись и часовой пояс;
- `tasks` — текст дела, статус, срок, правило повтора и настройки настойчивости;
- `push_subscriptions` — endpoint и криптографические ключи Web Push для каждого устройства; секретные данные подписки защищаются при хранении и не попадают в логи;
- `reminder_occurrences` — конкретные запланированные срабатывания, время UTC, статус, ключ идемпотентности и номер попытки;
- `delivery_attempts` — история попыток, ответ push-сервиса и время следующей попытки.

Время конкретной отправки хранится в UTC. Часовой пояс IANA пользователя, например `Europe/Moscow`, сохраняется отдельно, чтобы правильно создавать и отображать локальное расписание, включая повторяющиеся правила.

## Надёжность и повторы

Доставка push имеет семантику «как минимум один раз»: если процесс упал после принятия push-сервисом сообщения, но до записи результата в PostgreSQL, возможен повтор. Поэтому у каждого срабатывания должен быть стабильный idempotency key; обработчики должны безопасно переживать повторный запуск. Состояния отправки и срок аренды/обработки позволяют повторно подобрать задачи после падения worker.

Ошибки делятся на временные и постоянные. Для временных используется ограниченный экспоненциальный backoff с jitter; при исчерпании лимита задача переводится в конечное состояние и становится видимой для диагностики. Ответы push-сервисов, коды ошибок и число повторов сохраняются без записи секретов подписки.

Настойчивость — это правило приложения, а не бесконечные повторы Celery: например, первое уведомление в срок и ещё несколько повторов с заданным интервалом до выполнения или конечного времени. Каждое повторное уведомление — отдельное срабатывание в PostgreSQL.

## API и безопасность

API первой версии включает операции для регистрации/отзыва push-подписок, создания и изменения дел, завершения, переноса и получения списка дел, а также настройки повторов. Операция подписки требует аутентификации и CSRF-защиты там, где применяются cookie. Push endpoint и ключи подписки считаются чувствительными данными. VAPID private key используется только backend-ом.

PWA на iPhone должна быть добавлена на экран «Домой», пользователь должен явно разрешить уведомления, а service worker обязан показать видимое системное уведомление при получении push. Backend не может гарантировать, что пользователь увидел уведомление: он фиксирует принятие сообщения push-сервисом, а не факт прочтения человеком.

## Наблюдаемость и эксплуатация

Для первой версии нужны структурированные логи API и worker, health/readiness проверки PostgreSQL и RabbitMQ, а также фиксация ошибок отправки. Следует наблюдать за числом просроченных срабатываний, длиной очереди, числом повторов и возрастом самой старой необработанной отправки. База требует регулярных резервных копий и проверенного восстановления; RabbitMQ не заменяет backup данных расписания.

## Что сознательно не входит в первую версию

- Kafka: потоковая платформа для большого числа событий и нескольких независимых потребителей не нужна приложению напоминаний начального масштаба.
- Redis: отдельная потребность в кэше или брокере пока отсутствует; добавление создаст ещё один сервис.
- Микросервисы и отдельный сервис аутентификации: API и worker остаются частями одного backend-проекта.
- Гарантия точной секунды доставки или прочтения: время доставки зависит от worker, сети и push-сервиса платформы.

## Схема

```text
Next.js PWA ──HTTPS──> FastAPI ──> PostgreSQL
                            │           ▲
                            └─ Celery ─ RabbitMQ ─> Celery worker ──Web Push──> iPhone PWA
                                             ▲
                                       Celery Beat
                                  (проверка расписания)
```
