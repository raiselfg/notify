# Правила разработки

Эти требования обязательны для ИИ-агентов при работе с репозиторием.

## Перед написанием кода

- Сначала найди в репозитории похожие реализации через `rg` и `rg --files`, изучи связанный код и его тесты. Только после этого приступай к изменениям.
- Используй существующие реализации как образец: соблюдай принятые именование, структуру модулей, разделение ответственности, работу с зависимостями, обработку ошибок и стиль тестов.
- Переиспользуй подходящие функции, классы и схемы. Не дублируй готовую логику и не вводи новые архитектурные подходы, если задачу можно решить по существующим правилам проекта.
- Если похожей реализации нет, ориентируйся на ближайшие по назначению модули и настройки `pyproject.toml`.

## Объём изменений и diff

- Решай только поставленную задачу. Сначала изучи связанный код и существующие соглашения, затем внеси минимальные изменения, необходимые для результата.
- Сохраняй локальный стиль файла. Не форматируй весь файл или проект ради небольшого изменения и не включай в diff строки, изменённые только из-за форматирования.
- Не запускай форматтер в режиме исправления для всего проекта. Для проверки используй `uv run ruff format --check .`. Если форматирование требуется для изменённого кода, форматируй только затронутый файл, затем проверь diff и убери посторонние форматировочные изменения.
- Не делай несвязанные переименования, рефакторинг, перестановку импортов или правки комментариев. Если необходимое изменение затрагивает старый код, оставь его вне задачи, пока исправление не требуется для корректности или безопасности.
- Перед завершением просмотри `git diff` и `git status`. Проверь, что каждая изменённая строка относится к задаче, а пользовательские незакоммиченные изменения сохранены.
- Не меняй автоматически сгенерированные или lock-файлы без причины. Обновляй `uv.lock`, когда меняются зависимости, и сохраняй его синхронным с `pyproject.toml`.

## Python и проверки

- Проект рассчитан на Python 3.15. Используй существующую асинхронную архитектуру FastAPI и SQLAlchemy; не добавляй новую библиотеку, если задачу можно решить текущими зависимостями.
- Соблюдай настройки Ruff и Pyright из `pyproject.toml`: длина строки 88, двойные кавычки, строгая проверка типов. Не ослабляй настройки линтера или типизации, чтобы скрыть ошибку.
- Перед передачей изменений запусти относящиеся к ним проверки. Полный набор CI: `uv run ruff check .`, `uv run ruff format --check .`, `uv run pyright`, `uv run pytest`. Если проверка не запускается, укажи причину; не объявляй её пройденной.
- Запускай команды из корня репозитория:
  - Линтер: `uv run ruff check .`.
  - Проверка форматирования без изменения файлов: `uv run ruff format --check .`.
  - Форматирование только затронутого Python-файла: `uv run ruff format app/path/to/changed_file.py` (замени путь на фактический).
  - Проверка типов: `uv run pyright`.
  - Все тесты: `uv run pytest`.
  - Тесты затронутой функциональности: `uv run pytest tests/test_changed_feature.py` (замени путь на фактический).
- Добавляй или меняй тесты для нового поведения и исправлений, особенно для ошибок аутентификации, границ доступа и обработки сбоев. Не подменяй проверку поведения тестом, который лишь повторяет реализацию.

## Безопасность

- Не помещай пароли, токены, ключи и другие секреты в код, тестовые фикстуры с реальными данными, логи, коммиты или сообщения об ошибках. Конфигурацию и секреты получай из настроек окружения; в примерах используй явно фиктивные значения.
- Не логируй пароль, исходный токен сессии, заголовок авторизации или строку подключения с паролем. Для хранения сессий сохраняй только хеш токена; возвращай исходный токен клиенту только в предусмотренном API-потоке.
- Пароли хешируй существующим безопасным механизмом из `app/core/security.py`; никогда не храни и не сравнивай их в открытом виде. Не раскрывай, существует ли учётная запись, через различающиеся ответы входа.
- Формируй запросы через SQLAlchemy и передавай значения параметрами. Не вставляй пользовательский ввод в SQL, shell-команды, пути или HTML без подходящего безопасного API и проверки.
- Проверяй входные данные на границах API через Pydantic-схемы. Для ошибок возвращай только необходимую клиенту информацию, не выдавай трассировки, внутренние детали БД или секреты.
- Сохраняй ограничения доступа и целостности в базе данных. Изменения схемы оформляй новой миграцией Alembic; не переписывай уже применённые миграции без явной необходимости.
- Не отключай TLS, проверку сертификатов, авторизацию, ограничения CORS или защитные проверки ради удобства разработки. Для локальной разработки используй безопасные фиктивные настройки.

## Работа с данными и зависимостями

- Не удаляй и не перезаписывай пользовательские данные. Изменения схемы должны учитывать существующие записи и иметь безопасный порядок миграции.
- Используй транзакции и откат при ошибках записи. Не подавляй исключения молча; преобразуй их на соответствующем уровне, сохраняя причину для внутренней диагностики без утечки клиенту.
- Добавляй только необходимые зависимости и фиксируй их через `uv`. Не выполняй сетевые загрузки, публикацию, деплой или операции с внешними системами без соответствующего запроса.
