# Автоматические веб-пуши

Очередь хранится в PostgreSQL, отдельный брокер не нужен. API и worker запускаются
отдельными процессами и используют одну базу и одинаковые VAPID-настройки.

После настройки окружения примените миграции:

```bash
uv run alembic upgrade head
```

Запустите обработчик из корня проекта:

```bash
uv run python -m app.worker
```

Для отправки нужны корректные VAPID-настройки и сохранённая браузерная подписка.
Worker откажется запускаться без VAPID. Он запускает реальные отправки для всех
наступивших незавершённых задач. Браузеру по-прежнему нужен service worker,
который отображает уведомление. Настройка HTTPS и публичного ключа клиента
описана в [документации отправщика](web-push-sending.md).

## Хранение и обработка

- `push_events` хранит событие: задачу, версию расписания, исходное время
  напоминания, снимок заголовка и срок актуальности.
- `push_deliveries` хранит отдельную доставку для каждой подписки, число попыток,
  время следующей попытки, срок и токен временного закрепления за worker.
- Создание события, доставок и перенос `next_reminder_at` выполняются в одной
  транзакции. После простоя создаётся одно событие, исходная сетка интервалов
  сохраняется. Без подписок расписание тоже переносится, событие помечается
  `no_subscriptions`; позднее добавленные устройства не получают старые события.
- Worker выбирает записи через `FOR UPDATE SKIP LOCKED`. Можно запускать несколько
  процессов: они пропускают строки, занятые другими обработчиками. Сеть работает
  после завершения транзакции БД.
- Срок закрепления доставки: таймаут отправки плюс 30 секунд. Он обновляется
  при подготовке. После падения worker доставка снова доступна по истечении
  срока. Счётчик попыток увеличивается при захвате, включая попытки, прерванные
  аварией до сетевой отправки. Старый токен не может подтвердить новую попытку.
- Перед каждой попыткой проверяются состояние задачи, версия расписания и
  принадлежность существующей подписки. Завершение и изменение интервала отменяют
  старые доставки при их следующей обработке. Удаление задачи удаляет её события
  и доставки каскадно. Отписка прекращает использование подписки.
- Ошибка одного устройства не повторяет успешные отправки на другие устройства.
  При `404/410` удаляется только неизменившаяся подписка. История доставок остаётся,
  ссылка на удалённую подписку становится пустой.

## Повторы и ограничения

Статусы: `pending`, `processing`, `accepted`, `failed`, `expired`, `cancelled`,
`invalid_subscription`. `accepted` означает принятие push-сервисом, а не показ.

По умолчанию допускается 5 попыток. Между временными сбоями — 30, 60, 120 и
240 секунд плюс случайная добавка до 10%. Корректный `Retry-After` задаёт
минимальную задержку. Повтор за пределами срока актуальности не назначается;
`401/403` и прочие постоянные ошибки не повторяются. Исчерпание попыток, в том
числе после аварий, переводит доставку в `failed`.

Срок актуальности события ограничен следующим напоминанием и `PUSH_TTL_SECONDS`
от момента создания события. После ошибки неудачная доставка возвращается в
`pending`, сохраняя диагностический HTTP-код или безопасную причину сбоя.

Настройки окружения:

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `PUSH_POLL_SECONDS` | 5 | Пауза, когда нет работы или цикл завершился ошибкой |
| `PUSH_MAX_CONCURRENCY` | 10 | Размер партии и параллелизм одного worker |
| `PUSH_MAX_ATTEMPTS` | 5 | Лимит попыток одной доставки (1–20) |
| `PUSH_TIMEOUT_SECONDS` | 10 | Таймаут попытки и основа срока закрепления |
| `PUSH_TTL_SECONDS` | 3600 | Максимальный срок актуальности события |

`SIGINT` и `SIGTERM` прекращают новые циклы после завершения текущего. При
принудительной остановке незавершённые попытки восстанавливаются по сроку
закрепления. Ошибки цикла журналируются без SQL-параметров, ключей и endpoints.

Если push-сервис принял сообщение, а процесс упал до фиксации результата в БД,
повтор возможен. Идентификатор события сохраняется; клиент должен использовать
его для дедупликации и `tag` для замены уведомления задачи. Уже начатый запрос или
принятое push-сервисом сообщение нельзя гарантированно отозвать при завершении
задачи. История очереди автоматически не очищается.

## Проверка

Интеграционные тесты требуют `TEST_DATABASE_URL` в формате
`postgresql+asyncpg://USER:PASSWORD@HOST:PORT/DATABASE`, указывающий на отдельную
тестовую БД с правом создания схем. Каждый тест создаёт случайную схему
`test_push_*`, применяет миграции и удаляет только свою схему при завершении.
Не используйте рабочую БД для тестов.

```bash
uv run pytest tests/test_push_queue.py -v
```

Без `TEST_DATABASE_URL` эти тесты пропускаются с пояснением. CI запускает их
на отдельном PostgreSQL. Они проверяют реальные блокировки, миграции, откат,
восстановление, отмену и частичные сбои. Отправщик подменён: реальных пушей нет.
